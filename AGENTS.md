# Repository Agent Rules

These rules apply to every human or automated contributor in this repository.

## Read before acting

Read completely, in this order:

1. `AGENTS.md`
2. `docs/PROJECT_STATE.md`
3. `docs/DESIGN.md`
4. relevant domain baseline: `docs/REQUIREMENTS.md`, the applicable files under `docs/design/`, `docs/IMPLEMENTATION_PLAN.md`, domain sources/tests, and every applicable accepted ADR under `docs/decisions/`
5. the assigned `docs/tasks/<TASK-ID>.md`, when implementation tasks exist

If required documents disagree or are missing, stop at the affected boundary and ask the integration owner. Do not invent a substitute contract.

## Durable context is mandatory

- Never depend on chat history, agent memory, or an earlier context window. They are not project state.
- Persist every requirement, decision, assumption, verification result, blocker, and next action needed by another agent.
- Stable IDs are required and must reuse the namespaces in `docs/REQUIREMENTS.md`: for example `DATA-ROUNDTRIP-001` or `NAV-HISTORY-001` for requirements, `P2-HISTORY-01` for tasks, `RT-001` / `SAFE-003` / `AC-NAV-001` for tests or acceptance evidence, and `ADR-NNNN` for decisions. Do not invent parallel `REQ-*` or `TEST-*` IDs in a task note.
- At task start, copy `docs/tasks/TEMPLATE.md` to `docs/tasks/<TASK-ID>.md` (or refresh the existing note), then update only that task's `docs/PROJECT_STATE.md` entry to `CLAIMED` with owner, IDs, scope, base revision, and baseline evidence.
- At task end, handoff, block, review, or imminent context compaction, update the task note and `PROJECT_STATE.md` with head revision, exact verification evidence, unresolved questions, and the next owner/action.
- Re-read `PROJECT_STATE.md` immediately before applying a surgical state patch. Never reformat or overwrite another task entry. Only Integration marks a task `DONE`.
- Clarified product behavior goes into `REQUIREMENTS.md`; architecture/contract decisions go into an ADR. A chat agreement is not accepted until persisted.

The standard handoff template and evidence requirements are in `docs/IMPLEMENTATION_PLAN.md`. Use them verbatim. “Tests pass”, “mostly done”, and “see chat” are invalid handoffs.

If `.codegraph/` exists, use CodeGraph before `rg` or manual file reading when locating or understanding code. Otherwise use `rg`/`rg --files` first.

## Task and ownership rules

- Work only on a claimed task ID with one accountable owner and explicit paths.
- The only pre-Git exception is the initial checkpoint of `P0-BOOT-01`: use base revision `unversioned`, initialize and commit the validated privacy-safe design baseline, then return to one-task/one-branch-or-worktree rules before any parallel implementation.
- Inspect the working tree first. Existing changes belong to someone else unless provenance is certain.
- Do not discard, rewrite, format, rename, or include unrelated changes.
- Cross-owner edits require prior coordination and a recorded handoff.
- Only the integration owner changes root manifests, lockfiles, global CI, release configuration, and central milestone state unless the task explicitly delegates them.
- Use isolated `docs/tasks/<TASK-ID>.md` notes for detail; edit `PROJECT_STATE.md` only at required start/end checkpoints and never use the implementation plan as a status log.

Default directory ownership:

| Path | Owner |
|---|---|
| `src-tauri/src/commands/**` | Native Command API |
| `src-tauri/src/application/**` | Native application/use-case layer |
| `src-tauri/src/domain/**` | Contract/Domain |
| `src-tauri/src/infrastructure/**` | Native platform adapters |
| `src/domain/**` | Handwritten frontend domain models |
| `src/generated/**` | Generated by Contract/Domain; never hand-edit |
| `src/app/**` | Resource router, sessions, tabs, history, flags |
| `src/features/editor/**` | Editor |
| `src/features/workspace/**` | Workspace shell/navigation |
| `src/features/assets/**` | Clipboard/image assets |
| `src/features/diagrams/**` | Rich render/diagram viewer |
| `src/infrastructure/tauri/**` | Typed frontend IPC adapter |
| `tests/contract/**` | Contract/Domain + QA |
| `tests/integration/**`, `tests/e2e/**`, `tests/fixtures/**` | QA, with feature-owner review |
| `docs/design/**`, `docs/decisions/**` | Design/Architecture owner + Integration review |

When work must cross these boundaries, freeze or reuse an interface first. Do not solve a coordination problem by coupling directories.

## Contracts and decisions

- Architecture/domain documents and accepted ADRs are the source of truth, not the most convenient existing implementation.
- Do not change frozen IPC, domain models, state machines, revision/conflict rules, persistence formats, trust boundaries, or performance budgets without an accepted ADR.
- Core command names and envelopes are versioned. Breaking changes require version/migration decisions and contract tests.
- `src/generated/ipc.ts` comes from the Rust schema. Regenerate it; never patch it manually.
- New dependencies, parsers, renderers, network behavior, or storage systems require architecture and security review.
- Preserve `DocumentSession != Tab != ViewState` and Markdown-as-source invariants.

ADR path: `docs/decisions/NNNN-short-title.md`. Include status, context, decision, alternatives, consequences, migration/rollback, security/data impact, affected contracts, and tests. Accepted ADRs are immutable history; supersede them with a new ADR.

## Implementation constraints

- Keep commits narrow and prefix them with the task ID.
- No drive-by refactors, mass formatting, or unrelated dependency upgrades.
- All incomplete user-visible work stays behind a typed feature flag. Safety flags fail closed.
- Frontend code does not read arbitrary files or pass image/file binaries as Base64 IPC. Rust owns filesystem and clipboard binary operations.
- UI entry points use `ResourceRouter`; they do not navigate resources with ad hoc paths or `window.location`.
- Renderers/widgets do not mutate document sessions directly. They use the frozen editor/render boundary.
- Preserve cancellation, typed errors, and sequence/revision checks through every async layer.

## Test requirements

Before handoff, run formatting, lint, typecheck, Rust checks, focused unit tests, relevant contract/integration/E2E tests, and schema-drift checks. Add tests for success, failure, cancellation, and stale-revision behavior where applicable.

For any documentation or contract change, first run `ruby scripts/validate_design_docs.rb`. It reads repository Markdown only and is the minimum gate for links, fences, stable IDs, UX crosswalk, acceptance references, IPC command names, status leakage, personal paths, and embedded Base64. Once implementation tooling exists, this check is additive and never replaces the build/test gates below.

Record evidence under its repository test/acceptance ID: exact command, relevant OS/tool versions, base/head revision, exit/result, failing test names, and artifact/log path. State explicitly why any required check was not run. Evidence in chat does not count.

Additional mandatory gates:

- editor changes: CJK IME/composition, undo/redo, selection, and source round-trip;
- file/save changes: fault injection proves the original remains intact;
- navigation changes: shared session plus independent history/view-state tests;
- asset changes: disk-full/permission/cancel/undo/staging/rollback tests;
- renderer changes: timeout, size limit, sanitization, source fallback, and accessibility;
- parser/index/performance changes: documented time and memory budget comparison.

Do not weaken, skip, or rewrite a failing test merely to make a branch green. Update a golden fixture only with an intentional behavior decision and reviewer approval.

## Data safety and security

- Treat Markdown, HTML, SVG, Mermaid, links, filenames, workspaces, clipboard data, and recovery state as untrusted input.
- Inspect large/unsafe input before it enters JavaScript or the editor.
- Saves and repairs use scoped temporary files, durable write/flush, validation, and atomic replacement. A failure must leave the original recoverable.
- Never overwrite an external disk revision without an explicit revision check and user-approved conflict action.
- Never recursively delete broad or unresolved paths. Prefer trash/recoverable operations and delayed, scoped orphan cleanup.
- Do not commit or log user documents, clipboard contents, secrets, personal absolute paths, full file contents, or giant Base64 fixtures. Generate hazardous fixtures at test time.
- No document data leaves the machine without an explicit product requirement, accepted security ADR, and informed user action.
- Sanitize rendered HTML/SVG and restrict external resources. A renderer failure falls back to editable source.

## Handoff

Use the standard template in `docs/IMPLEMENTATION_PLAN.md`. In `docs/tasks/<TASK-ID>.md`, record requirement/test/ADR IDs, base and head revisions, touched paths, completed and remaining criteria, exact validation evidence, flag/contract versions, decisions/assumptions, unresolved questions with owners, temporary artifacts/recovery, and one recommended next action. Mirror the compact terminal state into `docs/PROJECT_STATE.md`. Never describe an unbuildable or partial branch as complete.
